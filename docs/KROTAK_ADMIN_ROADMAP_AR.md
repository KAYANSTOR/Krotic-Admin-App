# خارطة طريق كروتك برو — لوحة الإدارة من الصفر حتى الإغلاق

**الهدف:** إغلاق تطوير مركز إدارة كروتك برو في لوحة الإدارة أولًا، ثم بدء تغييرات تطبيق Android وفق الخطة المنفصلة في مستودع التطبيق. هذه الوثيقة خطة تنفيذ مرحلية ومعايير قبول؛ لا تعني أن كل البنود قد نُفذت.

**فروع العمل:**
- لوحة الإدارة: `feature/krotak-admin-control-center`
- خطة Android فقط (لا تغييرات كود Android الآن): `plan/krotak-android-template-sync`
- يمنع الدفع إلى `main`. جميع العمل والتحديثات والمراجعات تكون على فرع الميزة المحدد فقط.

## 0. تعريف الوضع القائم وحماية خط الأساس

- لوحة الإدارة React/Vite، وتستخدم Firebase Authentication وCloud Firestore وواجهات خادمية على Vercel.
- مصدر الإعدادات العامة الموجود هو `app_settings/global_config`. توجد بيانات المستخدمين في `users/{uid}` وأجهزة FCM في `users/{uid}/devices/{deviceId}` وسجل التدقيق في `admin_audit_logs`.
- تطبيق Flutter يعمل محليًا أولًا. المحافظ وقوالب التحويل مخزنة محليًا في Drift (`wallets` و`transfer_templates`)، وتوجد إعدادات الرسائل في `app_settings` المحلي. المعالجة الحالية للرسائل محلية.
- لا يوجد Supabase في هذا التكامل. يمنع إنشاء جداول SQL أو مجموعات Firestore بديلة لمجرد سهولة الواجهة قبل إثبات الحاجة.
- قبل كل مرحلة: فحص `git status`, مراجعة diff، التأكد من الفرع الصحيح، وإجراء نسخة احتياطية/نقطة استعادة محلية. لا حذف أو إعادة تسمية لحقول قائمة.

**معيار الإغلاق:** تقرير يحدد المصدر لكل حقل، ومستخدميه، وصلاحياته، ومستهلكيه في إصدار التطبيق الحالي، وقائمة اختبارات الأساس. كل تغيير على الفرع وليس `main`.

## 1. تثبيت عقد البيانات والصلاحيات

- وضع عقد إصدار واحد للقوالب يصف: `schemaVersion`, `releaseId`, رقم الإصدار، الحالة، وقت/مدير النشر، حد توافق محرك التطبيق، نطاق التوزيع، المحافظ، القوالب، والمتغيرات المسموحة.
- قوالب عامة للجميع هي الأساس؛ يسمح بتجاوز خاص بالشبكة. قاعدة الحسم ثابتة: تخصيص شبكة صالح ومفعّل، وإلا القالب العام المنشور، وإلا رفض التحليل بأمان مع سجل سبب.
- تجنب تعارض مفاتيح الإعداد العام المالي/الاشتراكات. لا يُسمح لعملاء المستخدمين بكتابة إصدارات منشورة أو حالة الترخيص. نشر إعدادات المركز يتم عبر API خادمي يتحقق من المدير.
- مطابقة كل مخطط مع العقود المحلية الحالية في Flutter قبل اعتماد serialization. لا تغيير إلى Drift schema إلا بعد إثبات الحاجة وخطة ترقية/تراجع.
- إصدارات التطبيق المثبتة تقارير غير موثوقة لحظيًا: تُعرض على أنها آخر إبلاغ مع تاريخ الإبلاغ، ولا يستنتج الإصدار من APK المنشور أو FCM token.

**معيار الإغلاق:** وثيقة JSON/TypeScript/Dart contract مع أمثلة توافق، وقواعد Firestore وAPI tests تثبت صلاحيات المدير والمالك ومستخدم عادي.

**حالة لوحة الإدارة (2026-10-19):** أضيف عقد عربي في
`TEMPLATE_CENTER_CONTRACT_AR.md`، API إداري للمسودات والمحاكاة والنشر والتراجع
والتوزيع، وقواعد تمنع وصول العميل المباشر إلى مجموعات مركز القوالب. تبقى
اختبارات GitHub Actions ومراجعة الحقول الفعلية على قاعدة البيانات شرطًا قبل
اعتماد المرحلة. لم يُنفذ أو يُعدّل مستهلك Flutter.

## 2. مركز إدارة المحافظ

- صفحة RTL للجوال والحاسوب لقائمة المحافظ مع البحث/الفرز، حالة المحفظة ومصدر الرسائل.
- إنشاء وتعديل وتعطيل/أرشفة المحفظة، والاسم والشعار/اللون إن كانا مدعومين، ومعرّف ثابت، SMS/notifications، sender ID واسم الحزمة عند الحاجة.
- ربط القوالب بالمحفظة والتحقق من عدم تغيير معرّف محفظة مستخدمة بما يفصل التاريخ أو القوالب.
- منع التفعيل الإنتاجي لمحفظة جديدة قبل اكتمال اختبار مصدر الرسائل؛ إبقاء أي تعريف تجريبي غير موزع.
- سجل تدقيق لمن أنشأ أو عدل أو عطّل المحفظة ومتى.

**معيار الإغلاق:** CRUD خادمي/مصرح، اختبار محرر، اختبارات قواعد، حالات تحميل/فراغ/خطأ/صلاحية، واختبار توافق المعرّفات القديمة.

**حالة التنفيذ:** محرر RTL للمحافظ أضيف ضمن صفحة مركز القوالب، وتخزينه حتى الآن
داخل مسودة/إصدار مركزي غير مستهلك من Flutter. لم يُنفذ استيراد آلي لتعريفات
المحافظ القديمة أو مزامنة Drift.

## 3. قوالب تحليل التحويلات ومختبر المحاكاة

- واجهة القوالب تشمل المحفظة، الاسم، النطاق (عام/شبكة)، النمط، الأولوية، الحقول المستخرجة، الحقول الإلزامية، Sender ID، sample message، وحالة التفعيل.
- استخدام صيغة نمط متوافقة مع المحرك الحالي. لا يُسمح بتخزين regex أو إعداد لا يفهمه التطبيق الحالي؛ كل نوع تحويل/استخراج مدعوم يجب أن يكون صريحًا ومختبرًا.
- مختبر محاكاة يبين القالب الذي طابق العينة والقيم المستخرجة وسبب الرفض. عينات الاختبار منزوعة البيانات الحساسة.
- حواجز ضد تعارض الأولوية، regex مكلف/خطير، غياب المرجع الإلزامي، القيم غير المنطقية، ومحاولات إعادة استعمال الرسالة.
- لا ينتج عن نجاح المطابقة وحده أي إيداع أو أثر مالي؛ تظل idempotency والتحقق من المصدر وقيود المحرك المحلي سارية.

**معيار الإغلاق:** عينات صحيحة وخاطئة ومتشابهة ومكررة، واختبار parser حقيقي ضد محرك Flutter قبل النشر.

**حالة التنفيذ:** محرر قوالب التحويل ومحاكاة خادمية محدودة أضيفا باستخدام
الحقول والرموز التي طوبقت مع مستودع Flutter على GitHub. المحاكاة ليست بديلًا عن
اختبار القبول بمحرك Flutter ولا تنفذ أثرًا ماليًا.

## 4. قوالب الرسائل الصادرة

- فصل قوالب العملاء/النظام/POS عن قوالب تحليل الرسائل الواردة.
- إظهار نوع الرسالة، النطاق، اللغة/الشبكة، المتغيرات المسموحة والإلزامية، ومعاينة عربية بعد الاستبدال.
- الرفض عند وجود متغير مجهول أو مفقود، ودعم حروف عربية وأرقام عربية/لاتينية والنص الطويل.
- لا تتجاوز القوالب المركزية التخصيصات المحلية التي لا تزال ضرورية للعمل دون اتصال؛ تحدد سياسة الدمج صراحة.

**معيار الإغلاق:** كل قالب لديه عقد متغيرات، preview tests، واختبار إرسال تجريبي لا يرسل فعليًا إلى عميل قبل التأكيد.

**حالة التنفيذ:** أضيف محرر ومعاينة محلية للرسائل الصادرة، مع قائمة مفاتيح
المتغيرات المعتمدة وفصل النطاقات. يظل التحقق النهائي من التطابق مع سجل Flutter
على GitHub مطلوبًا قبل إعلان التوافق.

## 5. التوزيع العام وتخصيص الشبكات

- يختار التطبيق الإصدار العام المنشور افتراضيًا، ويطبق override للشبكة فقط إذا كان منشورًا وصالحًا ومتوافقًا.
- حفظ قائمة الشبكات التي تستخدم القالب العام والتي لها override، مع إمكانية البحث والتصفية.
- فشل تحميل override أو عدم توافقه لا يعطل القوالب المحلية؛ يعود التطبيق إلى آخر نسخة سليمة محلية وفق العقد، لا إلى تخمين.
- التحكم في الاستهداف لا يستعمل للتلاعب بتراخيص الحساب؛ بيانات الترخيص تظل من مصدرها القائم.

**معيار الإغلاق:** اختبارات precedence، fallback، offline، missing/invalid payload، وتوافق إصدار التطبيق.

## 6. مسودات وإصدارات ونشر وتراجع

- كل تعديل يبدأ مسودة؛ الحفظ لا يعني النشر.
- خطوات النشر: تحقق schema والصلاحيات، تشغيل المحاكاة/حالات الاختبار، عرض diff، تأكيد المدير، إنشاء release immutable، ثم تحديث pointer النشط ذريًا.
- الاحتفاظ بسجل إصدار append-only: المالك/المدير، الوقت، نطاق الشبكة، hashes أو diff، حالة الاختبار، سبب النشر/التراجع.
- التراجع ينشئ release جديدًا يعيد pointer إلى محتوى سابق صالح؛ لا يمحو التاريخ ولا يغير سجلات المعالجة السابقة.
- احتفظ بآخر إصدار معروف صالح، ومنع تحديث جزئي أو payload يتجاوز حدود Firestore. لا تُحفظ مصفوفة تاريخ بلا حد داخل وثيقة واحدة.

**معيار الإغلاق:** اختبارات publish وrollback والتعارض concurrent edits وفشل API، مع تدقيق غير قابل للتعديل من العميل العادي.

## 7. صفحة المستخدمين وإصدارات التطبيق

- عرض الإصدار وversionCode المثبتين كما أبلغ بهما التطبيق، آخر ظهور، آخر وقت مزامنة، وبيانات الجهاز/Android إذا أرسلها التطبيق فعلًا.
- مقارنة مع الإصدار المنشور وتحديد: محدّث، إصدار قديم، أو لم يرسل بيانات إصدار. الإصدار المنشور لا يثبت أنه مثبت.
- بيان الترخيص ساري/منتهي/موقوف من حقول الوصول الموجودة فقط، وعدم استنتاجه من بيانات الجهاز.
- سجل أجهزة/إصدارات مع تاريخ الإبلاغ، بحث وفرز حسب الإصدار والحالة.
- في الفرع الحالي أضيف دعم `app_latest_version` و`app_latest_version_code` في `app_settings/global_config`، وعرض/فرز/بحث المستخدمين، وحقول الإصدار في أجهزة المستخدم. إرسال Flutter الفعلي لهذه القيم ينتظر خطة التطبيق؛ لا تُعلن الميزة كدليل لحظي.
- طراز الجهاز وإصدار Android غير موجودين ضمن البيانات المثبتة في مصدر التطبيق عند التدقيق؛ لا تعرضهما كمتاحين حتى تنفيذ الإبلاغ واختباره.

**معيار الإغلاق:** حساب اختبار على إصدار قديم وآخر جديد وجهاز لم يرسل إصدارًا، مع سجل تواريخ موثق، وتأكيد حماية بيانات المستخدم.

## 8. ربط المزامنة على Android — بعد إغلاق لوحة الإدارة واعتماد عقدها

هذه المرحلة موصوفة فقط في الفرع المنفصل للموبايل. لا تنفذ ضمن فرع لوحة الإدارة الحالي. بعد إغلاق اللوحة، يُحدّث Flutter ليقرأ الإصدار المنشور ويتحقق منه ويخزن آخر نسخة سليمة محليًا دون تعطيل المعالجة المحلية. راجع وثيقة الخطة في مستودع التطبيق.

## 9. التحقق والقبول قبل إغلاق لوحة الإدارة

- `npm test`, `npm run lint`, `npm run build`, ومحاكي Firebase Rules.
- اختبارات API والصلاحيات، CRUD للمحافظ، عقد القوالب، محاكاة الرسائل، precedence العام/الشبكة، سجل النشر والتراجع.
- اختبارات توافق على بيانات قديمة، فشل الشبكة، نسخة تطبيق قديمة لا تعرف حقولًا جديدة، واسترجاع آخر إعداد محلي صالح.
- مراجعة diff للأمن والبيانات الحساسة والـ logs. لا بيانات حقيقية في عينات الاختبار.
- اختبار بيئة تطوير ببيانات اصطناعية فقط. بعد نجاح جميع المعايير، مراجعة PR إلى فرع العمل، ثم موافقة المستخدم الصريحة قبل نشر/دمج production. لا دفع إلى `main` في هذا العمل.

**معيار إغلاق المشروع:** كل البنود المرحلية معتمدة، جميع الاختبارات اللازمة خضراء (أو كل استثناء موثق ومقبول)، تقرير تنفيذ نهائي، مراجعة بشرية، وقرار نشر منفصل.
