# حالة توقيع الجهاز وAttestation وTLS Pinning

**التاريخ:** 2026-10-27
**النطاق:** مستودع لوحة الإدارة `KAYANSTOR/Krotic-Admin-App` فقط.
**الخلاصة:** هذه الطبقة **غير منفّذة**، ولا يفرض الخادم أي ترويسة أو متطلب جديد عليها. لا يجوز وصفها بأنها حماية فعالة حتى تكتمل المتطلبات أدناه وتُختبر على جهاز فعلي.

## 1) ما هو موجود فعلاً

| العنصر | الحالة | الدليل |
|---|---|---|
| Firebase ID Token على المسارات الخادمية | منفّذ | `server/_lib/entitlementActivation.js`, `api/sales/ingest.js`, `api/device-heartbeat.js` |
| ربط الاستحقاق بـ`installationId` | منفّذ | `users/{uid}.entitlementInstallationId` + `entitlementVersion` |
| HMAC لرفع المبيعات | منفّذ | `x-verification-receipt` في `api/sales/ingest.js` |
| تدوير مفتاح الشبكة مع مهلة | منفّذ | `server/_lib/networkSecretStore.js` |
| توقيع جهاز مستقل (Device Key) | **غير منفّذ** | لا يوجد توليد مفتاح جهاز أو توقيع طلب في هذا المستودع |
| Play Integrity / Key Attestation | **غير منفّذ** | لا يوجد أي مرجع `attestation` أو `integrity` في كود الخادم |
| TLS Pinning في تطبيق Android | **غير منفّذ في هذا المستودع** | تطبيق Flutter مستودع منفصل ولم يُعدّل |

## 2) ما لا يفعله الخادم الآن

- لا يطلب ترويسة توقيع جهاز، ولا يتحقق من سلسلة شهادات Android.
- لا يعتبر نجاح Firebase ID Token إثباتاً لسلامة الجهاز.
- لا يمنح صلاحيات إضافية بناءً على نبض الجهاز؛ النبض مراقبة فقط.

## 3) متطلبات التنفيذ قبل أي فرض خادمي

1. **في تطبيق Android:** إنشاء زوج مفاتيح داخل Android Keystore، وتسجيل المفتاح العام للجهاز على الخادم بعد أول تفعيل.
2. **توقيع الطلبات:** توقيع `method + path + timestamp + nonce + sha256(body)` بمفتاح الجهاز، وإرسال `X-Device-Key-Id`, `X-Device-Timestamp`, `X-Device-Nonce`, `X-Device-Signature`.
3. **Attestation:** إرسال Play Integrity token أو Key Attestation certificate chain، والتحقق الخادمي من الحزمة والتوقيع و`nonce` ومنع إعادة الاستخدام.
4. **TLS Pinning:** تثبيت شهادة/مفتاح النطاق في تطبيق Android مع خطة تدوير، وعدم تفعيله قبل اختبار جهاز حقيقي.
5. **الطرح التدريجي:** مفتاح خادمي `DEVICE_ATTESTATION_MODE=off|monitor|enforce`، والبدء بـ`monitor` وتسجيل الرفض دون منع، ثم `enforce` بعد التأكد أن كل إصدارات التطبيق المدعومة ترسل الترويسات.
6. **الاختبارات:** جهاز متجذر/محاكي يجب أن يُرفض في `enforce`، وجهاز سليم يجب أن ينجح، وإعادة nonce يجب أن تُرفض.

## 4) قرار هذه الجولة

لم تُضف أي ترويسة إلزامية جديدة، لأن التطبيق الحالي لا يرسلها بعد، وأي فرض مفاجئ سيقطع المبيعات والتفعيل. تبقى هذه الطبقة **عملًا متبقيًا** موثقًا، وليست ادعاءً بحماية قائمة.
