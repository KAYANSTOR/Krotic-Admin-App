# عقد مركز القوالب والنشر (مصادر الرسائل والرسائل)

> **المصطلح:** ما يسميه Android جدول `wallets` هو هنا **«مصدر الرسائل»**، وليس
> محفظة مالية ولا يحمل رصيدًا. الاسم التقني `wallets` يبقى في العقد والحمولة
> وDrift للتوافق فقط. راجع `docs/TEMPLATE_CENTER_STYLE_AUDIT_AR.md` للمعجم
> الكامل وقواعد الصياغة.

**الحالة:** عقد تنفيذي للوحة الإدارة، تمت مطابقته مع `main` في مستودع
`KAYANSTOR/Krotak-Pro` عند الالتزام `e070d6a0df160d84b1bc0dea7589744d4b9b3d85`
(2026-10-19). هذه قراءة مرجعية فقط؛ لا يغيّر العمل في هذا الفرع أي ملف Flutter.

## حدود المصدر الحالي

تظل قاعدة Drift المحلية مصدر التشغيل الحالي في Flutter. لا تكتب لوحة الإدارة
إلى قاعدة التطبيق المحلية، ولا تعدّل `app_settings/global_config` أو بيانات
المبيعات/العمولات لهذا الغرض. أي نشر مركزي يصبح متاحًا للتطبيق بعد إصدار Flutter
يدعم قراءة العقد والتحقق منه وحفظ آخر نسخة سليمة محليًا. وحتى ذلك الحين، تعرض
اللوحة حالة التوزيع على أنها غير مستهلكة من التطبيق.

## مطابقة النماذج المحلية

### مصدر الرسائل (جدول `wallets`)

جدول `wallets` المحلي يحتوي:

| الحقل | النوع | القيد/المعنى |
|---|---|---|
| `id` | string | المفتاح الأساسي؛ ثابت بعد إنشاء مصدر الرسائل ولا يعاد استخدامه |
| `name` | string | الاسم المعروض |
| `status` | string | `active` أو `suspended` أو `archived` |
| `createdAt` | datetime | وقت الإنشاء المحلي |

تحفظ `senderId` و`sourceMode` و`packageName` في JSON داخل إعداد
`wallet_extras` keyed by wallet id، وليس كأعمدة في جدول `wallets`.
`sourceMode` هو `sms` أو `notification`. يجب الحفاظ على مفاتيح مصادر الرسائل الحالية
عند الاستيراد أو التصدير، وعدم تفسير القيم الغائبة على أنها مصدر إشعارات؛
القيمة المحلية الافتراضية هي `sms`.

### قالب التحويل الوارد

الأعمدة الأساسية في `transfer_templates` هي `id`, `name`, `pattern`,
`is_active`. أضيفت إليها محليًا `wallet_id`, `priority`, `sample_body`,
`sender_code`, `identifier_kind`, `pos_id`, `sender_name_label`, `note_label`,
`require_reference`.

`identifier_kind` يقبل `phone`, `alternativeNumber`, `account`,
`senderNameOnly`, `balanceRequestCode`. نتيجة التحليل قد تحمل
`isAlternateIdentifier`; هذه قيمة مشتقة وليست حقلًا في قالب التحويل.
يستخدم المحلل الرموز `{amount}`, `{phone}`, `{account}`, `{ref}`, `{qty}`,
`{dest}`، ويدعم الصيغة القديمة `%name` لهذه الرموز. الأرقام العربية/الهندية
والفواصل المرنة تطبّع محليًا. ترتيب المحاولة هو `priority` تصاعديًا ثم الاسم.
يرفض المحلل المبلغ غير الموجب، والمرجع المفقود عندما `requireReference`،
والكمية خارج 1–20، وأرقام الهاتف غير الصالحة. قوالب طلب الرصيد وعمليات POS
لها قواعد خاصة موثقة في محرك Flutter؛ لا يعاد تنفيذها بتعبير عام غير محدود في
الخادم.

### الرسائل الصادرة

قوالب النظام معرفة في `OutboundTemplateCatalog`، ونصوصها في إعدادات التطبيق
المحلية. توجد مفاتيح مستقلة للرسائل المخصصة ولمؤشر القالب النشط؛ النص لا يُكتب
فوق قالب النظام. يسجل `TemplateVariableRegistry` المفاتيح القانونية والمرادفات
والنطاق ومصدر ربط المتغير. النطاقات منفصلة: `inboundWalletParse`,
`inboundPosParse`, `outboundCustomer`, `outboundPos`, `outboundSystem`.
الفئات المعروفة: `customers`, `offers`, `pos`, `salafni`, `system`. يدعم
العارض المحلي `{name}` و`%name`، ويرفض الإرسال إذا بقي متغير غير محلول أو كان
النص الناتج فارغًا. لا تعتمد اللوحة متغيرًا خارج السجل، ولا تسمح بتكرار
مرادفين لنفس المفتاح القانوني أو بخلط نطاق الوارد والصادر.

لا يخلط هذا العقد الرسائل الصادرة بقوالب تحليل SMS الواردة، ولا يفرض مزامنة
مركزية فوق التخصيصات المحلية أو سلوك العمل دون اتصال.

## بنية الإصدار المركزي

تستخدم لوحة الإدارة مجموعات منفصلة عن الإعدادات المالية:

- `template_center_drafts/{draftId}`: مسودة قابلة للتعديل.
- `template_center_releases/{releaseId}`: سجل إصدار غير قابل للتعديل بعد النشر.
- `template_center_pointers/{scopeKey}`: المؤشر النشط لنطاق `global` أو شبكة
  محددة. تحديثه ذري مع إنشاء الإصدار.

كل وثيقة إصدار تحمل `schemaVersion`, `releaseId`, `version`, `versionCode`,
`status`,
`createdAt`, `createdBy`, `publishedAt`, `publishedBy`, `scope`,
`minAppVersion`, `minAppBuild`, `payload` وملخص hash. يحتوي `payload` على
`wallets`, `transferTemplates`, و`outboundTemplates`. معرفات مصادر الرسائل والقوالب
ثابتة؛ تغيير الاسم أو الحالة لا ينشئ هوية جديدة. لا يجوز وضع البيانات المالية
أو حالة الترخيص في الحمولة.

كل كتابة مركزية تمر بواجهة خادمية تتحقق من المدير. قواعد Firestore تمنع كتابة
العميل مباشرة للمسودات والإصدارات والمؤشرات. الإصدار المنشور append-only.
التراجع ينشئ إصدارًا جديدًا بمحتوى إصدار سابق صالح ويحدّث المؤشر في معاملة؛ لا
يحذف سجلًا ولا يعيد كتابة معالجة مالية سابقة.

## واجهات الإدارة والتوزيع الحالية

تنفّذ لوحة الإدارة هذه العمليات عبر `POST /api/template-center`:

| `action` | الصلاحية | السلوك |
|---|---|---|
| `catalog` | مدير | يعيد أنواع المعرّف ومفاتيح الرسائل ومتغيراتها المسموحة للمحرر. |
| `list`, `list-networks` | مدير | يعرض المسودات والإصدارات والمؤشرات والشبكات. |
| `save-draft`, `delete-draft` | مدير | يحفظ مسودة أو يحذفها مع سجل تدقيق ذري. |
| `simulate-inbound`, `preview-outbound` | مدير | يتحقق ويعاين دون إرسال أو تنفيذ مالي. |
| `publish` | مدير | يتحقق من الحمولة والتوافق، ثم ينشئ إصدارًا غير قابل للتغيير ويحدّث المؤشر ويسجل التدقيق في معاملة واحدة. |
| `rollback` | مدير | ينشئ إصدارًا جديدًا من حمولة إصدار سابق، مع مقارنة المؤشر المتوقع لمنع الكتابة المتزامنة. |
| `read-active` | مستخدم مصادق | يعيد override الشبكة المتوافق ثم الإصدار العام المتوافق، أو `null` عند عدم وجود إصدار صالح. |

تُحفظ بيانات الإصدار مع `createdAt`, `createdBy`, `publishedAt`,
`publishedBy`, `payloadHashSha256`, `minAppVersion` و`minAppBuild`. رقم
`versionCode` يتزايد لكل نطاق. طلب `read-active` لا يقرأ المسودات، ويرفض
الإصدارات ذات بيانات التوافق أو الحمولة غير الصالحة. إذا كان الإصدار يتطلب حدًا
أدنى غير صفري ولم يرسل العميل رقم التطبيق المطلوب، ينتقل الاختيار إلى النطاق
العام بدل تسليم إصدار غير متحقق من توافقه.

لا تفتح قواعد Firestore قراءة العميل لهذه المجموعات؛ القراءة المخصصة للأجهزة
تمر بواجهة `read-active`. لم يُنفّذ مستهلك Flutter أو التخزين المحلي هنا، وهذا
العمل لم يغير مستودع التطبيق.

## قواعد الاختيار والتوافق

1. يستخدم عميل متوافق ومتحقق منه override الشبكة المنشور والصالح إن وجد.
2. عند غياب override أو عدم توافقه أو فساد حمولة قراءته، يختار إصدار `global`
   المنشور المتوافق.
3. عند تعذر قراءة الخادم، يستخدم التطبيق آخر إصدار مركزي سليم محفوظ محليًا؛
   لا يستبدل قوالبه المحلية ببيانات ناقصة.
4. عند عدم وجود إصدار مركزي صالح أو نسخة محلية سليمة، يرفض التغيير المركزي
   بأمان ويستمر وفق السلوك المحلي السابق؛ لا يخترع قالبًا ولا ينشئ عملية مالية.
5. نجاح محاكاة القالب لا يودع رصيدًا ولا يسجل بيعًا. تظل مفاتيح idempotency
   وحواجز المصدر ومسارات اعتماد العمليات قائمة.
6. الإصدار المبلّغ عنه من التطبيق معلومة تشخيصية غير موثوقة، لا إثبات تثبيت أو
   ترخيص. الجاهزية الفعلية للمزامنة لا تُعلن قبل وجود مستهلك Flutter متوافق.

## حالات القبول للوحة الإدارة

- رفض المعرفات المكررة والروابط إلى مصدر رسائل غير موجود والأنواع/الرموز المجهولة.
- عدم السماح بتفعيل قالب تحويل يفتقد المتطلبات التي يفرضها المحلل المحلي.
- المحاكاة قراءة فقط: تعرض نتيجة المطابقة والحقول المستخرجة أو سبب الرفض، ولا
  تستدعي معالجة رسالة أو مسارًا ماليًا.
- معاينة الرسائل الصادرة ترفض المتغيرات المجهولة أو المطلوبة المفقودة، ولا ترسل
  SMS أو FCM.
- رفض النشر عند اختلاف المؤشر المتوقع (تعارض تحرير متزامن)، وعند فشل التحقق أو
  تجاوز حد الحمولة.
- تحقق أن عميلًا عاديًا لا يستطيع قراءة المسودات أو كتابة أي وثيقة إصدار/مؤشر؛
  ويطلب من واجهة التوزيع الإصدارات المنشورة فقط بعد مصادقة مناسبة. لا يعني ذلك
  أن تطبيق Android الحالي يستهلك هذه الواجهة.
